# Beta acceptance checklist

The candidate can be inspected now. Distribution requires `review.json` to say `releaseReady: true` for the exact extension/engine/Seatline hashes. Pending fields in `evidence-template.json` are not approvals. The release command recomputes quality from referenced response/label/judgment artifacts and refuses incomplete, fixture or stale evidence.

1. Independently review every corpus reference (326 proofreading cases, 36 distinct-source rewrites across six modes and 18 clearer-wording cases), including ambiguous, already-correct, informal, second-language and Unicode text. For every case explicitly record an approved, corrected or rejected decision. Approved references match the proposal, corrected references must differ, and rejection blocks release until the corpus is repaired. A review header alone cannot approve labels. Use a pseudonymous reviewer ID and an ISO review timestamp.
2. Prepare a configuration-bound acceptance policy without provider calls (`--prepare`) and independently approve a meaningful minimum exact-reference recall before the live run. No recall floor is preapproved by the candidate. Run the production prompt/validator against each proposed live Codex model/CLI/runtime configuration. Independently judge every emitted suggestion, explanation and whole-output meaning. Require at least 95% human proofreading precision, report exact-reference recall separately and meet the preapproved floor, and preserve protected facts/negation and rewrite meaning. All six rewrite modes (improve, paraphrase, clearer, shorter, formal and friendly) must be reviewed, and clearer wording is judged on its own: at least 95% human precision over its emitted suggestions (offering none does not pass), reported apart from the proofreading numbers, and shorter outputs must reduce length. Malformed model answers are counted while the runner continues; infrastructure/limit failures stop without retry. Review available partial-run outputs and leave unavailable rows explicitly unreviewed; incomplete runs remain blocked. A perfect fixture or an all-empty response cannot qualify.
3. Review current Linux/macOS installed-extension CI editing/privacy/limits/frame/keyboard results. Record the actual commit, Actions URL and current package/engine hashes.
4. On actual hardware, use Lineleaf concurrently with a second existing authorized consumer through one shared companion. Use distinguishable synthetic drafts. Verify routing/session isolation, app-scoped cancellation/revocation, recovery, one Lineleaf active turn and shared automatic budget across tabs/restarts. No cross-consumer output or automatic retry/replay may occur. Do not deliberately exhaust live quotas.
5. Measure at least 30 live requests for each qualified configuration, document cold/warm phases and hardware, and approve the completion-p95 and incremental typing-overhead-p95 limits before accepting results. Record matching configuration hashes. Synthetic dispatch measurements cannot establish device or provider responsiveness.
6. For each platform to advertise (desktop Chrome on Linux and/or macOS), personally verify install, stable-identity update with preserved preferences/grants, uninstall/storage removal, Chrome's native permission prompt, revoke, pause, reset, a successful native round trip, keyboard accept/undo and screen-reader navigation/announcements. Record exact browser/OS versions and current package hash. Chromium CI preapproval is not permission-prompt acceptance.
7. Verify authenticated synthetic drafts in Gmail, GitHub, LinkedIn and Slack. Record verified replacement or verified Copy fallback for each. Record caret, formatting, controlled state, undo, dynamic navigation and failure behavior. Google Docs replacement is outside this candidate.
8. Complete the pending evidence fields only after those checks. The repository's evaluation guide describes scoring and `--evidence` use. Run the release command; any missing gate exits 2 and removes a stale generated beta ZIP. A passing command emits a loadable beta ZIP and a review archive with the support/acceptance material.

Human review fields are accountable attestations checked for completeness and artifact consistency, not proof of a person's identity or cryptographic authentication of CI/device results. The release owner must inspect the named evidence and reviewer independence. Unit-test approvals exist only in memory and are never shipping evidence.
