# C-01–C-05 — opt-in inline development prototype

This slice adds automatic paragraph proofreading to the [selection prototype](selection-mvp.md). It uses the same shared Seatline companion, stable extension identity, optional site grants, Codex subscription/tool-isolation gates, ephemeral turns, and validated editor adapter. No companion or native protocol changes are required. This is development behavior; live quality/latency, device setup, real editor compatibility, and human screen-reader acceptance remain open.

> **Interface.** The badge, underlines, card, panel, popup and settings page were redesigned on 2026-10-03; see [Interface design](interface-design.md) for how they look and behave now. The behaviour described below is unchanged except where that page says otherwise (the Tab order inside a suggestion now reaches Accept first).

## Try the flow

Run `npm ci --ignore-scripts`, `npm run package`, and load `dist/lineleaf` unpacked in desktop Chrome. The ZIP is `dist/lineleaf-0.1.0.zip`. Existing load/setup instructions and Seatline authorization are in the selection guide.

1. Enable one ordinary HTTP/HTTPS site in the popup.
2. Open Settings and explicitly enable **Automatically check after typing pauses (experimental)** after reading the provider disclosure. Automatic mode defaults off, including after upgrading an existing enabled-site profile.
3. Type in an eligible input, textarea, or basic inline contenteditable. After 1.5 seconds of idle time, Lineleaf checks the current newline-delimited paragraph, up to 2,000 UTF-16 code units. Focusing prefilled text or moving the caret alone sends nothing.
4. Click an underline or the Lineleaf badge, or press **Alt+Shift+L**. Use Tab/Enter to review and accept, dismiss, copy, or add a spelling token to the dictionary. Escape closes the card and returns focus to the field. Changes always require acceptance.
5. Use **Undo last edit** before subsequent typing. **Check now** makes an explicit paragraph check; the selection panel supports the six deliberately requested style rewrites for a selection.
6. Pause globally from a card or popup, resume in popup/settings, or disable the site. Reset removes stored preferences, dictionary, enabled sites, and optional site access; automatic mode returns to off.

Only supported, visible, writable fields in eligible same-origin HTTP(S) documents are checked. D-02 includes permitted same-origin child frames and active fields in open shadow roots; cross-origin/opaque frames and closed roots remain excluded. Password/payment, ignored or hidden content, code/preformatted content and oversized paragraphs use the existing manual/copy boundary. Complex and rich contenteditable editors get the inline checking described [below](#rich-editor-inline-checking): Accept in verified editor families, copy-only elsewhere. The active field may be held locally as an exact-source snapshot up to 100,000 code units; only its bounded active paragraph is sent. A caret move to another paragraph before idle cancels that scheduled source rather than sending unrelated text. Synthetic page events invalidate work but cannot authorize an automatic check.

When a text field refuses an edit (a maxlength, a site handler) and the adapter rolls it back, the card says the original text was restored and keeps the suggestion or rewrite preview with **Copy** for as long as the text is unchanged. The rollback itself raises the adapter's revision and marks the field copy-only, so the capture is replaced by a copy-mode snapshot; before this was done the 250 ms poll cleared the card about a quarter of a second after the failure. Typing clears it as usual.

A manual selection opened while an inline card has focus retains the original field selection. Live-region text changes only on message transitions, not on each keystroke. Human screen-reader validation remains open.

Lineleaf does not mutate the field to draw underlines. Identity transforms and translations retain aligned overlays, including translated roots and clipping ancestors. Scale, rotation, skew, perspective or shaped clipping prevent inline mounting/checking; use the manual selection panel. Vertical writing does not get a guessed underline. Harmless field/ancestor class and style changes redraw geometry without discarding suggestions. Text/tree changes and safety-marker or context changes still invalidate captures, including remove/reinsert and marker/slot ABA. Exact source, revision, inline formatting, unique context, Unicode boundaries, non-overlap, and supported native replacement are checked again before acceptance. Failed replacement restores the source when possible and keeps Copy available.

## Request and data lifecycle

There is one active writing turn across Lineleaf documents. Preference/site/dictionary writes are serialized; pause from either popup or settings changes only pause and takes effect immediately. Settings Save sends only edited model/variant/automatic fields, compares their loaded values with current values, and reports a reload-required conflict if the same field changed elsewhere. Dictionary additions/removals merge into the current words; a stale options tab cannot wipe newer additions. Starts of automatic attempts, including failed status probes, count toward the shared budget; refreshes and worker restarts cannot bypass it. Provider rate limits use a bounded sixty-second cooldown and queue-full uses five seconds. Their timestamps also survive service-worker restarts in session storage. Terminal host, sign-in, malformed-output, and timeout errors stop automatic retries until explicit checking or a fresh eligible context. Reconnecting the network does not automatically resend the draft.

Typing, composition, site disable/revocation, pause/settings changes, page navigation, and field removal clear previews and cancel in-flight work. Moving on does not: clicking or tabbing to another control or another part of the page, switching tabs, and switching to another application leave what was found where it is. A request that is running finishes, and its result is there when the user is back; underlines are hidden only while the field is scrolled out of view, and nothing new is read or sent from a hidden page. Moving to another field sets the old field's suggestions aside in memory and brings them back, without a request, when the user returns and that paragraph is exactly as it was checked (text, place and editor must match; a changed paragraph gets none). Set-aside suggestions are never stored or sent anywhere, belong to the page and go with it, and end on the same events. There is no time limit: what a check found (and a rewrite preview) lasts for as long as the text it describes is unchanged and the page is open, and goes the moment that text changes; a failed check's message stays until the next action. Late output is ignored. Native turns have a ninety-second provider deadline when you asked and thirty seconds for a background check; the UI has a watchdog of 125 and 65 seconds respectively, which is the worker's whole sequence (ten-second handshake, fifteen-second status, the provider turn, three-second cancel drain) plus a seven-second margin, so the worker's own answer always arrives first. After a provider timeout, background checks stop for five minutes across tabs and worker restarts (or until a request you make gets an answer); a request you make is never held back. No field text, model output, credentials, or draft history is written to storage or logs. Stored local preferences intentionally include dictionary words and site origins; dictionary words are disclosed as being sent with checks. Session storage holds only pacing/backoff timestamps.

Dictionary matching uses normalized whole-word tokens and their English possessive forms (for Turkish, see [Turkish proofreading](#turkish-proofreading-f-04)). For a spelling candidate spanning multiple words, the common unchanged prefix/suffix narrows the changed range: a protected token in that range suppresses the whole candidate; a dictionary word elsewhere in the span does not suppress an unrelated spelling fix. This is a conservative text filter, not semantic classification of model output; linguistic correctness and explanation accuracy remain C-03/E-01 verification work.

## Rich-editor inline checking

Editors that are not flat text with inline formatting (Draft.js — X/Twitter's composer — Lexical, Slate, ProseMirror, Quill, Gmail, LinkedIn, Slack, Notion and any other contenteditable surface) offered only the manual panel. With the same separate automatic opt-in they now show inline underlines and a card for the paragraph the caret is in. Two tiers apply:

- **Verified families get Accept.** An editor whose root carries a Draft.js (`.public-DraftEditor-content`), Lexical (`[data-lexical-editor]`), Slate (`[data-slate-editor]`), ProseMirror (`.ProseMirror`) or Quill (`.ql-editor`) marker can apply a suggestion in place, like a spell checker.
- **Everything else is copy-only.** Other contenteditable editors, any editor on Gmail, LinkedIn, Slack or Notion hosts, editors inside shadow roots, and any editor that ever misbehaves show suggestions to read and copy; Lineleaf never writes to them.

| Aspect | Behavior |
| --- | --- |
| Request | After the usual 1.5 s pause following trusted typing, the caret's paragraph (one block or `<br>`/newline-delimited line, 1–2,000 characters, containing a letter) is sent. Other paragraphs of the same editor are never sent. Pacing, caps, cancellation, consent, dictionary and variant are identical to text fields. |
| Typing detection | Trusted `beforeinput`, `input` and composition events. Draft.js, Lexical and Slate cancel `beforeinput` and re-render, so no native `input` event may follow; the paragraph is read one task later and a check is armed only if it really changed (an editor that rejects a keystroke, for example at `maxlength`, arms nothing and leaves an already armed check alone). Caret movement alone sends nothing, and moving to another paragraph before the pause cancels the check. |
| Text mapping | The paragraph is read from the DOM without relying on framework markup: block and `<br>` boundaries become line breaks, zero-width placeholders are skipped, non-breaking spaces become spaces, and collapsible whitespace is reduced the way CSS renders it (one space; none at the start or end of a line; preserved under `white-space: pre*`), so the request matches the visible text even for pretty-printed markup or a space that is the only content of an inline element. Non-editable islands (mentions) keep their visible text. |
| Display | Underlines are placed from DOM ranges recomputed from the live nodes on each draw, so framework re-renders do not misplace them. In a verified family the card offers Accept, Dismiss, Copy, dictionary and navigation; in a copy-only editor it has no Accept and says so. |
| Applying a suggestion | Lineleaf focuses the editor, selects the exact range of the suggestion, waits for the editor to register that selection, then offers the edit as a cancelable `beforeinput` (`insertText`, or `deleteContentBackward` for a removal). An editor that takes it (Slate; Lexical for deletions) updates its own model. Otherwise the same edit runs as a native `insertText`/`delete` command, which Draft.js, ProseMirror, Quill and Lexical (insertions) reconcile from the DOM. Lineleaf never writes DOM nodes. A native command alone would leave Slate's model unchanged while its DOM shows the new text, which is why the offer comes first. **When the edit replaces all of a text node's text** (a whole-paragraph or whole-selection rewrite of a one-leaf block, as in X's composer), it is delivered as two edits: the new text is inserted after the old, then the old text is deleted. One replace-everything command makes the browser remove the emptied node; Draft.js then keeps a model that no longer reaches the page, and the text can be neither typed over nor deleted. The editor's own history holds two entries for such a replacement, so the status says undo takes two presses. The second step is verified, and if it does not take, or the page is not as expected between the steps, the inserted text is taken back out so the draft is never left as old text followed by new text (if that cannot be done the editor is marked copy-only and the status says to check the draft). Text whose spacing the editor would collapse, or that contains non-breaking or zero-width characters, cannot be verified and is refused with nothing changed. After the edit the caret returns to the position remembered when the card was open, not the one the focus change left. |
| What can be applied | The suggestion must match the checked paragraph exactly, lie inside one text node (a change across bold, a mention or another leaf boundary, or across collapsed or zero-width characters, is copy-only), be valid at the current revision and not be made during composition. Otherwise Accept is disabled and the card says Lineleaf can only copy it. |
| Verification and failure | The paragraph is re-read after the edit and must equal the expected text; the caret is restored to where it was (moved by the length change), and the paragraph is checked again 250 ms later to catch an editor that re-renders its old state. The checks read the paragraph that was edited, not wherever the caret is now. If the editor rejected the edit, produced unexpected text or reverted it, that editor becomes copy-only until the page reloads and the card says to check the draft. Lineleaf does not roll back: a wrong undo in a state-owning editor can do more harm than the failed edit. Typing during the 250 ms window is the user's, not a revert: the replacement and its left context must still be there and the original wording must not have come back; the caret is then left where the user put it and the paragraph is checked again after a pause. If the user moves to another field while the edit settles, Lineleaf hands off to that field and never pulls focus back. |
| Undo | There is no Lineleaf Undo in rich editors. The edit is an ordinary editor change, so the editor's own undo (Ctrl/⌘ Z) reverses it. |
| After Accept | Other suggestions for the paragraph that still point at the same words are kept and moved by the length change; the new text is not re-sent until the user types again. Focus returns to the editor. |
| Invalidation | A change to the checked paragraph (typing, or a site-driven rewrite), navigation, exclusion/ancestry/frame changes (including an excluded element such as `code` appearing inside the paragraph while a request is pending) or a lost field removes the preview or discards its result. Changes elsewhere in the editor do not. |
| Caret | The caret is remembered while the editor has it and restored when the card closes and before an explicit **Check now**, because Draft.js clears the DOM selection on blur and a mouse click on the badge blurs the editor before the click is handled. Moving focus into the card can make an editor react to blur/focus itself (for example ProseMirror's focus class). |
| Not eligible | Google Docs (any `docs.google.com` page), Monaco/CodeMirror/Ace and `pre`/`code` (the whole paragraph is withheld if it contains inline code), `aria-hidden`/`data-lineleaf-ignore` regions, password/payment-style fields, closed shadow roots and cross-origin/opaque frames. |

## Explicit rewrites in the inline card

The inline card (badge, an underline, or Alt Shift L) has a **Rewrite** row: **Improve it** and **Paraphrase**, then **Clearer**, **Shorter**, **More formal** and **Friendlier**. These are explicit actions that never run automatically, and they do not need the automatic opt-in: with it off, the card is built on demand ([F-03](#rewrites-without-the-automatic-opt-in-f-03)). The writing panel offers the same six modes, but only for a selection and with its compact before → after preview and Accept: Original/Suggested, Replace, Try again, Back and the paragraph fallback belong to the inline card.

| Aspect | Behavior |
| --- | --- |
| Scope | The selected text inside the field, otherwise the caret paragraph (1–2,000 UTF-16 code units containing a letter). Text fields and flat editors use their own selection offsets. In a rich editor a selection must sit inside one block and one line; Draft.js clears its DOM selection on blur, so the remembered range is restored first. Only an empty selection falls back to the paragraph: a selection that has no letters, spans paragraphs or lines, or is too long is refused with a message and nothing is sent. |
| Request | One explicit (`manual`) request through the same controller and Seatline path as a correction: no tools, ephemeral, no continuation, strict JSON `{"rewrite": …}`. An automatic request with a rewrite mode is refused. It bypasses the ten-second automatic interval, cancels an in-flight automatic check and still obeys provider limits and backoff. Improve it asks for clarity, concision and flow in the writer's voice, formality and rough length; Paraphrase asks for the same meaning in different words and structure, with the same tone and rough length. |
| Nothing to change | For Improve it and Paraphrase the model may return the text unchanged: the card says no change was suggested and keeps the proofreading suggestions that were set aside. The other four modes must return different text. |
| Preview | A rewrite replaces a whole selection or paragraph, so it is shown as **Original** and **Suggested** text with **Replace**, **Try again**, **Copy** and **Back**, never as an underline. Back, an empty result or a failure (a provider error, a lost connection, a failed connect or the timeout) restores the proofreading suggestions; a failed rewrite does not pause automatic checking. Typing, navigation, a changed paragraph or the five-minute expiry discard the preview. |
| Preservation check | Deterministic and advisory. Numbers and dates, names (capitalised words, counted by occurrence so dropping or adding a repeated mention is reported, including one that begins a sentence or the selection unless it is a common opener such as "The" or "Please"), @mentions, #tags, links, e-mail addresses and negations (compared word by word, so "not" becoming "never" is reported, and "n't" counts as "not") are compared between the source and the suggestion, and a difference adds "Check this version: it changes …" to the card (shortening may drop a number on purpose). It is a heuristic: a rewrite that drops an uncommon first word ("Quickly we left" → "Soon we left") is flagged as a name, a new capitalised first word is not treated as an added name, and spelled-out numbers and shifts of meaning that keep every tracked word are not detected, so the review stays human. |
| Replace | The same paths as a correction. Fields with the editing adapter replace natively and offer **Undo last edit**, which stays until you type (the adapter itself refuses it once the text has changed), including through the follow-up proofreading check; verified rich editors replace through their own input path (one text node only) and the editor's own undo reverses it; copy-only editors and the priority hosts show Copy only. A multiline result, or a rich paragraph that contains bold or a mention, is copy-only. After a replacement the new text, as the whole caret paragraph even when only a selection was rewritten, is proofread after a pause. |
| Not included | One suggestion per request ("Try again" asks again) and no custom tones. Optional clearer-wording underlines are a separate setting ([F-02](#optional-clearer-wording-suggestions-f-02)). |

Validation: unit tests cover the two modes' prompts and strict output (including "nothing to change" for only those two), the preservation flags and the refusal of automatic rewrite requests. `tests/rewrite.test.mjs` (19 browser regressions) covers paragraph and selection scope in a text field, every mode's request, flags, "no change" with the proofreading suggestions restored, Back and typing, a verified rich editor (paragraph and selection), a Slate-like editor that only trusts `beforeinput`, and copy-only editors. A panel test covers the new modes through the production worker. The E-01 corpus gained twelve reference rewrites (36 in total), and its fixture companion now matches the exact production prompt. ## Rewrites without the automatic opt-in (F-03)

**Decision.** Explicit rewrites do not require the automatic opt-in. That opt-in consents to Lineleaf reading and sending what you type without being asked, after a pause. A rewrite is the opposite: it sends only a selection (or the caret paragraph) after two deliberate actions, the shortcut and a button, in a card that names the provider and the remote-processing caveat. The site grant, the pause control, the exclusions and the bounded text are unchanged, so they, not the opt-in, are the gate. The writing panel stays the other explicit surface (selection only).

| Aspect | Behavior |
| --- | --- |
| Availability | An enabled, unpaused site (the same `site-state` answer as before) and an eligible field. A disabled or paused site, an excluded field or an excluded host builds nothing, and pausing removes an open card. |
| Trigger | **Alt Shift L** in the field. Focusing, typing, selecting, scrolling or moving the caret builds nothing, reads nothing and sends nothing; there is no badge or underline until then. Building the card checks only whether the field is eligible (a probe that does not read its text), and typing in the open card reads nothing either; the text is first read when an action in the card names what to check. The card closes when focus moves to another field, the site is paused or disabled, the page navigates, or five minutes after the last request; Alt Shift L builds it again. |
| What it offers | The same card: Rewrite row, **Check now** (one explicit proofreading request for the caret paragraph), Cancel, Pause, Settings; Original/Suggested with Replace, Try again, Copy and Back; the same adapter and verified-rich-editor Replace and the same copy-only previews (Gmail, LinkedIn, Slack, Notion). |
| Wording | The status says automatic checking is off and nothing is sent until an action. Editing the text afterwards says the text changed and to choose Check now or a rewrite; no follow-up proofreading is queued, not even after Replace. |
| Not changed | The automatic opt-in still gates everything unasked: the badge, underlines, the idle debounce, rich-editor previews while typing, and clearer wording. |

Validation: `tests/rewrite.test.mjs` (eight added browser regressions) shows that with automatic checking off typing builds no card and sends nothing even after longer than the idle window; instrumenting the field's `value` getter shows zero reads from typing, from opening the card and from typing in it, and reads only once Check now is chosen; Alt Shift L builds the card without a request; Improve it on a selection sends exactly one explicit request for that selection and Replace and Undo work; the replacement queues no check; Check now is one explicit proofreading request; a verified rich editor replaces through its own input path while a copy-only host only copies; pausing removes the card and the shortcut then does nothing; and the shortcut does nothing in an excluded field. Mutating the code to build the card on focus, or to poll with the automatic condition, fails these. Real sites, screen-reader use and human discoverability of the shortcut are **not** verified.

## Turkish proofreading (F-04)

Turkish is recognised from the text itself (see [Language detection](#language-detection-f-06)); there is nothing to choose. F-04 first shipped it as a third value of the `variant` preference (`TR`); that value is gone and a stored `TR` reads as US.

- **Proofreading.** Turkish gets the correctness check (grammar, spelling, punctuation), inline and in the writing panel. The prompt asks for standard modern Turkish (Turkish Language Association rules), forbids translating or changing the language, and asks for each explanation in Turkish. The card, labels and messages stay in English.
- **Rewrites and clearer wording.** [The Turkish preservation guard (F-05)](#turkish-preservation-guard-f-05) now covers these modes. All six explicit rewrites are available in the inline card and selection panel. Clearer wording still needs both automatic opt-ins and the shared request budget.
- **Dictionary.** For Turkish the personal dictionary treats dotted and dotless i as one letter (a sentence-initial "Işık" matches a stored "ışık"; the cost is that a stored word can also hide the misspelling that differs only by that dot), and takes the word before the apostrophe as the word, so "Ankara" covers "Ankara'da". An entry that shows Turkish letters (ç ğ ı İ ş) is lowercased with Turkish rules ("Işık" is stored as "ışık"), so the dictionary the provider receives spells the word as the text does; any other word lowercases the English way, where a capital I becomes i. The capital dotted İ is stored as a plain i for every language.
- **Validation.** Correction positions are matched by UTF-16 position and grapheme boundaries as for English, which is tested with ç ğ ı İ ö ş ü and a decomposed ş. Unit tests cover the setting, the prompt, language-aware validation and the dictionary; browser tests cover the inline card, the panel and the settings page. There is no reviewed Turkish evaluation corpus and no live-provider measurement, so quality, false-positive rate and the Turkish explanations are unverified.

## Turkish preservation guard (F-05)

`candidates` and `preservationFlags` require settings with a known English spelling (`US` or `UK`); omitted or unknown settings are refused. Which guard runs comes from the text (see [Language detection](#language-detection-f-06)) or from the `language` a caller has fixed; the evaluation runner and scorer fix each case's declared language. The Turkish guard lives entirely in the extension's worker. Page selection imports only the shared grapheme-boundary module, so page frames do not load the verb dictionary. It needs no additional provider request, companion change or runtime.

- **Explicit rewrites warn.** If a tracked number, name or negation differs, the before/after preview shows the existing “Check this version” message. Nothing is applied before Replace/Accept. The warning is advisory and allows a writer to review a deliberate change.
- **Automatic clearer wording drops.** A well-formed candidate that changes a tracked fact or negative clause is omitted. Validation compares the entire paragraph with and without the edit, including an edit to only part of a verb. An independent safe edit remains eligible. Malformed contracts, source ambiguity, overlaps and split graphemes still reject the response.
- **Turkish negation.** NFC normalization and Turkish casing precede Unicode word matching. The recognizer covers `değil`, `yok` and common inflections, `hayır`, `asla`, `hiç`, `hiçbir`, `kimse`, paired `ne … ne`, negative verb continuations after `-ma/-me` and progressive `-mıyor/-miyor/-muyor/-müyor`, negative ability and common voice extensions, and noun `-sız/-siz/-suz/-süz`, including apostrophe forms such as `Ali'siz`. Recognition also tries ASCII-folded words/stems with relaxed harmony where the keyboard spelling loses a vowel distinction (`degil`, `anlamiyorum`, `calismiyor`). Common informal `-mIcAm/-mIycAm` and `-mIyo/-mIyom/-mIyoz` endings are covered (`gelmicem`, `yapmıycam`, `bilmiyom`, `gelmiyo`). Signatures retain the actual normalized words, not folded approximations. Verbal recognition checks a known verb stem and harmony, so ordinary words such as `elma`, `kelime`, `malzeme`, `sinema` and positive infinitives such as `yemek` and `demek` are not classified by substring. Links, email addresses, mentions and suffixed proper names are excluded from verb recognition; they remain covered by the name/link check.
- **Scope is conservative.** Each recognized negative signal is bound to the words of its punctuation-delimited clause, in order. Paired `ne … ne` binds the whole sentence before splitting coordinated clauses, including `Ne yağmur yağdı, ne kar` and semicolon-separated pairs. A lone `ne` in each of two separate sentences is not paired. Moving the same `gelmedi` from Ali to Ayşe, or keeping one `değil` while attaching it to another predicate, warns/drops rather than passing a marker-count check. Canonical accents, Turkish casing, whitespace and apostrophe style are ignored. Wording changes inside a negative clause or paired-negation sentence, tense changes, harmless clause reordering and punctuation that changes the clause boundaries can also warn or be dropped. This is a conservative recognizer, **not** a complete morphological analyzer or proof of semantic equivalence: unknown roots, unsupported derivations, other colloquial spellings, stress-dependent readings and implied negation can escape it. English negation runs only under US/UK, so Turkish `not` (note) and `no` (number) do not get English warnings; mixed-language meaning still needs human review.
- **Ambiguity and noise.** Positive nominal inflections such as `yapmayı` and `gelmesini` are not negative endings. Bare nominal/imperative homonyms (`çalışma`, `gelme`, `gelmem`) remain **possible negation** signals bound to the word and its preceding context, not unrelated wording after it. Changing them warns explicitly as ambiguous and is still refused for automatic clarity; an unchanged `çalışma` does not suppress `acil bir şekilde` → `acilen`. Clear polar-question contexts suppress indefinite `hiç`/`kimse`. Disjunctive `yoksa` is excluded only after an earlier question particle, so conditional `Param yoksa … mi?` remains guarded. Repeated WH questions with `ne` immediately before recognized `istiyor`/`arıyor` predicates are excluded when no negative verb or question particle is present; a question mark alone does not exclude `Ne Ali ne Ayşe geldi?`. A title-cased `-maz/-mez` after a likely given name is treated as a surname (`Ahmet Yılmaz`, `Ayşe Durmaz`), not a verb; name counts still protect it. These bounded heuristics can misread rhetorical questions, unusual capitalization and other homographs. They reduce reported noise without certifying semantic equivalence or meeting the still-open human quality gate.
- **Names and numbers.** Turkish sentence openers have their own list, including keyboard spellings; proper names are counted by their base before straight or curly apostrophes (`Ankara'da` and `Ankara’ya` retain Ankara), with canonical accents normalized. Dropped, added or repeated names, mentions, links and numbers keep their existing flags. Both `%50` and `50%` retain their percentage sign. The capitalized-name heuristic can still overflag a sentence-initial verb or other uncommon opener; currency symbols and spelled-out amounts remain outside this numeric screen.
- **Proofreading and changed settings.** The F-04 proofreading language instruction and strict source-matching contract are retained; the new Turkish negation instruction is limited to style modes. The deterministic preservation filtering described here applies to style modes, as it does for English. Any saved variant change during a turn, including US ↔ UK, cancels stale delivery: an answer generated for the previous preference is not delivered under the new one, even if its storage notification is delayed.

The packaged verb-stem lexicon is derived from [Zemberek-NLP's master dictionary at `037202c7e18b977c95181a76db05cb1e95846554`](https://github.com/ahmetaa/zemberek-nlp/blob/037202c7e18b977c95181a76db05cb1e95846554/morphology/src/main/resources/tr/master-dictionary.dict), with 3,305 verb stems and voiced variants. The original project is copyright Ahmet A. Akın and Mehmet D. Akın, licensed Apache-2.0; the full license and Lineleaf's separate `zemberek-NOTICE.txt` attribution ship under `extension/licenses/`. The Apache appendix retains its standard template text; the notice carries the actual upstream copyright. Only dictionary data is derived; no Zemberek runtime is used. Regenerate it with `python3 scripts/generate-turkish-stems.py /path/to/master-dictionary.dict` from that revision. Its [negative transitions](https://github.com/ahmetaa/zemberek-nlp/blob/037202c7e18b977c95181a76db05cb1e95846554/morphology/src/main/java/zemberek/morphology/morphotactics/TurkishMorphotactics.java) informed the suffix cases. Both guard modules and the shared boundary module are included in the evaluation engine hash.

Validation: `tests/turkish.test.mjs` checks polarity additions/removals in all six rewrite modes, clause-scope changes, nominal lookalikes, Turkish casing and decomposed accents, apostrophe-base names, full-paragraph clarity filtering and unchanged English/proofreading behavior. Controller regressions verify that a Turkish text reaches the Turkish guard and both automatic opt-ins remain required. Browser regressions cover inline warnings, advisory previews, Replace/Undo, the selection panel, filtered automatic clarity and settings persistence. These are synthetic regressions; there is still no independently reviewed Turkish corpus, native-speaker review or live-provider precision evidence. F-05 remains IMPLEMENTED — VERIFY.

## Language detection (F-06)

English and Turkish work together with no language setting. Settings keep only the English spelling (US or UK); the language of each piece of text is worked out on the device from the text itself, in `extension/lib/language.mjs`. Nothing extra is sent to decide it, and the module is bundled into the worker only, not into page frames.

- **How it decides.** Turkish-only letters (ç ğ ı İ ş), common Turkish function words (also in their ASCII-typed spelling, `degil`, `icin`) and the present-tense ending `-(ı)yor` score for Turkish; common English function words and contractions score for English. A text is **English**, **Turkish** or **mixed** by the share of evidence, and **unknown** when there is too little to tell (a heading, a name, a number). A lone Turkish letter in an English sentence (a name such as Ayşe) does not make it Turkish.
- **What follows from the label.** The prompt: English text keeps exactly the instruction it always had; Turkish text gets the Turkish one; mixed text gets both languages' rules and the ban on translating; unknown text gets the same rules without claiming it mixes anything. For rewrites and clearer wording the last two also ask to preserve negation in both languages. Explanations are written in the language of the text they concern.
- **The meaning guards do not depend on which language wins.** A language's guard (English or Turkish negation, names and numbers) runs whenever that language has any evidence in the text, and both run when there is none, with a warning from either kept. An English sentence around a Turkish `gelmedim` therefore still has its negation checked, and doubt only adds warnings.
- **Dictionary.** Unless the text is plainly English the dictionary reads dotted and dotless i as one letter and a Turkish proper noun's apostrophe suffix as a suffix; mixed or unclear text accepts both readings. Entries are cased by the letters they show (see F-04).
- **Limits.** This is a heuristic, not a language identifier: it knows two languages, short Turkish text with no marker words is `unknown`, and a text that is mostly one language with a short phrase in the other is classified by its majority (the guards still see the phrase). It cannot split one paragraph into parts, so a mixed paragraph is handled as a whole. Adding a language means a letter test and a function-word list here, a prompt in `policy.mjs` and a meaning guard in `candidates.mjs`.
- **Validation.** `tests/language.test.mjs` (27 cases: English, Turkish with and without the special letters and in capitals, mixed, unknown, decomposed characters, odd input, speed) and controller regressions that send Turkish, English and mixed text through one session with no setting changed; browser regressions in the inline card and settings page. Each of thirteen deliberate breaks fails one of them. There is no independently reviewed corpus of Turkish or mixed text and no live-provider measurement, so the detector's accuracy on real writing, and the quality of the mixed-text prompt, are unverified.

## Optional clearer-wording suggestions (F-02)

A second, optional automatic check that underlines individual wording improvements (for example "in order to" → "to"), labelled apart from corrections. It is **off by default**, has its own setting and needs automatic checking.

**Cost decision.** It is a separate provider request, not extra fields in the correction request. A combined request would halve the cost but make one answer carry two contracts and hide the clearer-wording precision inside the correction precision. A separate request costs one more automatic provider call per checked paragraph, so it is gated behind its own setting, spends the same shared ten-second interval and six-attempts-per-minute cap (clearer wording therefore appears at least ten seconds after the corrections, and a busy writer gets fewer checks, not more traffic), and is disclosed in settings.

| Aspect | Behavior |
| --- | --- |
| Setting | **Also suggest clearer wording (experimental)** in settings. Stored as `clarity`, default off, off after reset and for profiles that predate it. It is on only while automatic checking is on: turning automatic checking off turns it off and it is not silently restored. The controller refuses a clearer-wording request unless both settings are on, refuses it from a manual request, and refuses automatic requests for any other mode. |
| Flow | After a correction result for a paragraph, whether an automatic one or one you asked for with Check now, Lineleaf sends that same paragraph once more with mode `clarity`, as an automatic request that waits for the shared interval. It is the second half of a check whose text was already sent, so it still runs if you have clicked elsewhere or left the field meanwhile: it uses the paragraph that was checked (never wherever the caret is now) and only while that paragraph is unchanged, and it waits for the field to be on screen. Typing, a changed paragraph, a rewrite or a new Check now cancels the wait; the new text gets its corrections first (and its own wording check). A shared-interval or busy refusal is retried once the interval allows; any other failure ends the attempt for that text, shows the reason and leaves the corrections on screen and automatic checking running. |
| Contract | Strict JSON `{"suggestions":[{"before","after","left","right","explanation"}]}`: at most eight, no category, no offsets, `before`/`after` at most 240 code units, the same exact-match and grapheme rules as corrections. Any violation rejects the whole answer as invalid output. |
| Held to a stricter bar | A well-formed suggestion is dropped, not flagged, when applying it to the paragraph changes a number, name, link or negation (the preservation check compares the whole paragraph with and without the edit, so "May" → "June" before "6" is caught, and names are counted by occurrence) or when it only changes spacing, punctuation or capitalisation (that is a correction). Overlaps with each other are invalid; overlaps with a correction are dropped on the page, so a correction always wins. |
| Display | Dashed blue underlines (`data-category="clarity"`) apart from the red, amber and solid correction underlines; the card is labelled "Clearer wording · Optional style"; the badge says how many of the suggestions are clearer wording. Accept, Dismiss, Copy and the editor rules are those of a correction (adapter fields and verified rich editors replace, others copy). |
| Measurement | Measured apart from proofreading in E-01: 18 clearer-wording reference cases (four deliberately empty: already clear, informal voice, ambiguous reference and a negation idiom that the preservation check must stop), `metrics.clarity` with its own reference precision and recall and human precision, a `CLARITY_PRECISION_GATE_NOT_MET` gate at the same 95% human bar, no clearer-wording cases in the proofreading strata, and the fixture companion matches the exact production prompt. |

Validation: unit tests cover the contract, the dropped-not-flagged rules, the prompt, the default-off and automatic-only setting, controller refusals and the shared budget (a clearer-wording request is refused inside the interval and counts toward the six-per-minute cap). `tests/clarity.test.mjs` (ten browser regressions) shows that with only automatic checking on a paragraph never gets a clearer-wording request, that with the setting on corrections come first and the wording request follows for the same text, that the two kinds are underlined and labelled apart and Accept works, that a wording suggestion overlapping a correction is not shown, that typing discards the pending check, that a failed, refused or dropped wording request keeps the corrections and does not pause automatic checking, that a change the editor reports without trusted typing ends the pending check, that accepting one correction still gets the remaining corrections re-checked, that nothing runs with automatic checking off, and that a verified rich editor accepts one through its own input path. The evaluation tests pin the separate metrics and gate. Mutating the controller gate, the setting normalisation, the preservation and formatting drops, the overlap rules, the follow-up scheduling, the failure handling or the typing reset each fails the matching test. Live precision and latency of clearer wording, real composers and screen-reader use are **not** verified: the references are unreviewed proposals, so F-02 stays IMPLEMENTED — VERIFY.

## When the provider is slow

A live report (a real X thread, Codex through Seatline) showed the card going quiet while "working", then returning with a timeout message and buttons that looked dead. Codex starts a process per turn, so a request can take longer than a second or two, and the first version of the card hid itself while it waited. Now:

- An action you take keeps the card open: the status names it, a line counts the seconds ("Waiting for Codex… 12 s"), the rewrite and **Check now** buttons are disabled so a second click cannot start another provider process, and **Cancel check** stays available. The counter is visual only; the status line is the live region.
- An action that cannot start says why in the card (a request is already running, text is being composed, an edit is being applied, the field is hidden, read-only or excluded, or **Check now** has no usable paragraph). A failure of an action you took, including a timeout, reopens the card with the reason instead of leaving only the badge.
- A request you made waits up to ninety seconds; a background check thirty. The timeout message says nothing was changed and suggests trying again, choosing a faster model or using **Check Seatline** in settings.
- Because each turn is a process on your machine, a timeout also stops background checks for five minutes (shared by all tabs, kept across worker restarts, ended by any request that gets an answer), so a provider that is not answering is not given more work. **Check now** and the rewrites still work. An editor whose background check is refused during the hold (another tab's timeout) is not left blocked: it tries again by itself when the hold ends, and the page watchdog covers the worker's whole sequence (handshake, status, turn and cancel drain), so a slow but healthy start cannot cost a valid answer.

Validation: the unit tests pin the 30- and 90-second limits, the hold (including a restarted worker and its expiry) and the watchdog bound (a 108-second sequence of slow handshake, status and turn still delivers; a status probe is cut off at fifteen seconds); `tests/rewrite.test.mjs` adds four browser regressions: progress, disabled actions and Cancel; a refused action saying why and then working; a timed-out Check now reopening the card and the next click working; and an automatic check refused during the hold being retried after it. Reverting each of these fails its test. The actual latency of Codex on the reporter's machine is **not** known: A-03 is still open, and the new limits are provisional.
